# Full codebase review — pass 3, 2026-04-27

This pass re-checks all findings from the two prior reviews, performs the §7.6
dead-code scan mandated by the updated review criteria, and surveys the effects
of three large refactor commits that landed between the April 27 fit-pipeline
review and this pass: the deletion of `fit/scout.rs`, `fit/refine.rs`,
`fit/validate.rs` (~2,000 lines), the deletion of `fit/status.rs` (~360 lines),
the collapse of the args submodule, and the workspace-wide dead-code cleanup
(~1,400 lines, all `#[allow(dead_code)]` cleared). Four findings were resolved
or documented by these commits; no new major findings were introduced. Twenty
prior findings remain open.

## Summary

**Strong:** The workspace-wide dead-code removal is a clear win — `voi.rs`,
`serve.rs`, and all their support scaffolding are gone; the `term::` module
is now precisely the two functions that are actually called; `allow(dead_code)`
has been eliminated from the entire Rust workspace. The deletion of the v1
stage entry points removes 2,000+ lines of dead code that had been silently
diverging from the live pipeline for weeks. ClM4 (refine.rs hardcoded 1.1
convergence threshold) and ClN5 (legacy scout path writing `resolved_gate:
None` without warning) are resolved by the deletion. The LaTeX test was
strengthened (TsN2 partial). The `Im18` heated-rung re-warmup is now visible
in logs.

**Needs work:** Twenty prior findings remain open. The most critical —
InM1 (ungrouped-transition gradient uses `rate <= 0.0` not `RATE_EPSILON`)
and ClM1 (legacy bridge silently discards `clean_eval`/`gate`) — have both
been explicitly identified in the prior two reviews and not addressed. The
worsened state of ClN1 (the `8.0` SE-floor multiplier now at 4 sites after
the gate-verdict logic was duplicated into `fit_summary.rs`) is a regression
from the prior review. The `#[allow(unused_variables)]` triplet surviving in
`if2.rs` is the sole remnant of the workspace `allow(dead_code)` sweep and
warrants immediate cleanup.

### Nit

#### ClN6 — Three `#[allow(unused_variables)]` for dead parameters in `camdl if2`

**File:** `rust/crates/cli/src/if2.rs:262–268`

```rust
// Observation model parameters (used by deprecated --obs-model fallback closures)
#[allow(unused_variables)]
let rho_idx = compiled.param_index.get("rho").copied();
#[allow(unused_variables)]
let k_idx = compiled.param_index.get("k").copied();
#[allow(unused_variables)]
let psi_idx = compiled.param_index.get("psi").copied();
```

These three bindings survived the workspace dead-code sweep because
`#[allow(unused_variables)]` is a per-binding attribute (not a per-item
`allow(dead_code)`) and the sweep targeted `dead_code` annotations. The
comment says "used by deprecated --obs-model fallback closures" but no such
closures exist in the current file. The values computed (`rho_idx`, `k_idx`,
`psi_idx`) are never read after their initialization. This is a §7.6 gap: a
named-reason comment exists (`"deprecated --obs-model fallback closures"`) but
the referenced code does not exist, making the keep-reason false. The correct
fix is to delete all three bindings and their `#[allow]` attributes.

**Impact:** Minor — no correctness risk. The three HashMap lookups execute on
every `camdl if2` invocation but cost nothing relative to model loading and
inference. The primary risk is that a future reader infers the `--obs-model`
flag is still partially functional.

### Worsened: ClN1 (updated severity from Nit to Minor)

The prior fit-pipeline review flagged the `8.0` SE-floor multiplier duplicated
at `gating.rs:162` and `gating.rs:236`. The implementation of `fit_summary.rs`
added two more independent copies of the same calculation:
`fit_summary.rs:289` (in `gate_verdict_block`) and `fit_summary.rs:686` (in
`stage_report`). All four are bare `8.0` literals:

```rust
// gating.rs:162:
let se_floor_db = 8.0 * sigma_max * NATS_TO_DB;
// gating.rs:236:
let se_floor_db = 8.0 * sigma_max * NATS_TO_DB;
// fit_summary.rs:289:
let se_floor_db = 8.0 * sigma_max * NATS_TO_DB;
// fit_summary.rs:686:
let se_floor_db = 8.0 * sm * NATS_TO_DB;
```

Changing this constant now requires edits to two files and four sites, with no
compile-time enforcement that they remain consistent. The finding is elevated
from Nit to Minor because four sites across two files increases the probability
of a future desynchronization. Define `const SE_FLOOR_K: f64 = 8.0` in a
shared location (either `evidence.rs` or `gating.rs` re-exported) and use it
at all four sites.

### Updated: ClN2 — three distinct `params_agree` implementations confirmed

The prior review identified two inconsistent implementations. Inspection now
reveals three:

1. **`params_agree` helper** (`fit_summary.rs:511–524`): symmetric scale
   `v.abs().max(other.abs()).max(1.0)` — correct.
2. **`provenance_block` text path** (`fit_summary.rs:434`): asymmetric
   `fv.abs().max(1.0)` where `fv` is the `final_params` value.
3. **`state_report` JSON path** (`fit_summary.rs:749`): asymmetric
   `fv.abs().max(1.0)` where `fv` is again the `final_params` value.

Paths 2 and 3 should call `params_agree` or a new `params_close(a, b, eps)
-> bool` helper instead of re-implementing the logic inline. Currently, if
both the state value and the final-params value are large and differ, paths 2
and 3 can disagree with path 1 about whether they match (path 1 normalizes by
the larger magnitude, paths 2 and 3 normalize by the final-params value only).

## Cross-cutting themes

**1. The two highest-priority open findings have now missed three review
cycles.** InM1 (ungrouped-transition gradient uses `rate <= 0.0` not
`RATE_EPSILON`) and ClM1 (legacy bridge silently discards `clean_eval`/`gate`)
were first identified in the April 24 review, re-confirmed in the April 27
fit-pipeline review, and confirmed again here. Both are correctness issues
in production inference paths — InM1 produces gradient/density mismatches
for any model with near-zero inflow rates; ClM1 silently resets user-configured
clean-eval and gate parameters to defaults when the legacy bridge is used.
These should be treated as blocking before the next model deployment.

**2. The dead-code cleanup was thorough and correctly scoped.** Commits
`e6ae9dba`, `f797985f`, `cd6e3d6e`, and `d9d5ab72` together removed
approximately 3,800 lines of dead code and cleared all `#[allow(dead_code)]`
from the workspace. The mechanism was sound: the cleanup deleted files in
dependency order (v1 stage drivers first, then helpers that only those files
needed, then workspace-level orphans), rather than suppressing warnings with
allows. The `ClN6` finding (unused_variables in if2.rs) is the sole remnant
that slipped through because it uses a different attribute. The cleanup
demonstrates that the repo can tolerate aggressive dead-code removal without
breaking the test suite — this discipline should continue.

**3. The verdict-computation duplication (ClM3, ClN1 worsened, ClN2) is
growing with each feature addition.** The fit_summary.rs implementation
duplicated the gate-verdict calculation from gating.rs rather than calling
into it. This is now the third time a rendering path has re-implemented a
computation that already exists elsewhere (gate verdict, SE floor, params
agreement). The right design is a pure `GateVerdictSummary` intermediate type
computed once and rendered by each format. This pattern is documented in the
prior reviews; it has not been adopted. Each new format that renders gate
data (text, JSON, Markdown, LaTeX) will multiply the duplication further.

**4. The 8.0 SE-floor multiplier now has four independent implementations.**
This is the most concrete symptom of theme 3. The prior review recommended
`const SE_FLOOR_K: f64 = 8.0` in one place. Instead, the summary renderer
added two more independent copies. If the proposal's "k=8 recommended default"
is ever revised to k=6 or k=10, three out of four sites will be silently wrong
until a user notices inconsistency between the gate verdict and the summary
output.

**5. OCaml compiler diagnostic quality remains a deferred debt.** OcM2 (no
loc field on dimcheck diagnostics), Ocm1 (no .mli interface files), Ocn1
(73 no_loc sites in expander.ml), and P2 (47 error codes with no golden
fixture) have all carried forward unchanged since the April 24 review. Unlike
the Rust dead-code cleanup, these OCaml items have no single targeted commit
addressing them. The risk is asymmetric: most OCaml changes are additive
(new error codes, new compiler passes), meaning the gap widens with each new
feature while no cleanup pass closes it.
