## Expansion (in progress): the full predictive family — filtering and smoothing

_Prepended draft. The v1 body below specs the one cell that shipped
(`free_forward × posterior`). This section widens the design to the filtering
and smoothing distributions so the verb family is designed as a whole. Concrete
column / enum spellings are deferred — a naming decision is open (see "Naming"
at the end of this section) — so this section names the **objects** and their
**sources**, not their wire labels._

A fitted state-space model supports a small, well-defined family of predictive
quantities, generated by three orthogonal axes:

- **Target — what quantity.** The _observation_ `y` (what the surveillance
  system records) or the _latent state_ `x` (the unobserved compartment counts
  behind it). This is a third axis the v1 framing folded into "horizon"; a
  latent state is not a horizon of the observation, it is a different target.
- **Conditioning — which data the quantity is conditioned on.** _Open-loop_: run
  the model forward from `t0`, never re-anchored to data (generative). _Filtered
  (past)_: conditioned on data up to the present — `x_t | y_{1:t}` for the
  state, `y_t | y_{1:t-1}` for the next observation. _Smoothed (all)_:
  conditioned on the whole series, `· | y_{1:T}`.
- **Parameter treatment.** _Posterior_ (average over the draw cloud) or
  _plug-in_ (a single parameter) — the existing safety axis (§"types first").

The cells that matter:

| target      | conditioning | object                                              | meaning                                                                                                                       | status                    |
| ----------- | ------------ | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| observation | open-loop    | **free-forward posterior predictive** (`y_rep`)     | "can the fitted generative model recreate data-shaped observations from `t0`?" — the harshest generative check                | **shipped (v1)**          |
| observation | filtered     | **one-step-ahead predictive** `p(y_t \| y_{1:t-1})` | "given data through `t-1`, can it predict the next observation?" — honest short-horizon adequacy, the basis for proper scores | implementable, no blocker |
| latent      | smoothed     | **smoothing distribution** `p(x_t \| y_{1:T})`      | "what latent trajectories are compatible with _all_ the data?"                                                                | data exists; gated        |
| latent      | filtered     | **filtering distribution** `p(x_t \| y_{1:t})`      | the online best estimate of the hidden state as data arrives                                                                  | needs new output          |

Why the whole family, not one cell: free-forward is the strictest check but says
nothing about _filtered_ predictive adequacy; the smoother is the most
flattering — conditioning on all the data can make a poor transition model look
plausible — so it must never stand alone. A generative check, an honest
forecast, and the compatible latent paths are different scientific objects, and
a typed `conditioning` (and `target`) column is what stops a reader from
overlaying one on another as if they were the same band.

### Where each comes from (and the real cost of each)

- **Free-forward predictive** — shipped. Forward-simulate each posterior draw,
  sample `y_rep` through the observation model, quantile (`fit predict`).
- **One-step-ahead predictive** — _moderate, no architectural blocker._ The
  particle filter already computes the one-step predictive `p(y_t | y_{1:t-1})`
  (it is the per-step normalizing constant). The lift is sampling `y_rep` one
  step ahead and folding it into the **same** observation artifact as
  `conditioning = filtered` rows. gh#269 is the plug-in (single-θ) version; the
  posterior version re-runs the filter per draw. Brings the proper-score columns
  (`log_score` / `crps` / randomized PIT), which are genuinely out-of-sample
  here (vs in-sample for free-forward).
- **Smoothing distribution** — _the data already exists; the lift is small but
  gated._ PGAS already writes conditioned latent trajectories `X_{0:T} | θ, y`
  (the shared `write_trajectories_tsv`, `conditioned = true`). A latent artifact
  is a quantile reduction of those draws per `(time, state)` — the **same**
  reduction `fit predict` runs for observations — written to a sibling
  `latent/<state>.tsv`. **Gate:** confirm the trajectory-coherence caveat
  (#270/#267 directional conservation, which this proposal flagged as making a
  naïve latent extractor "worse than none") is resolved before the artifact is
  trustworthy; and today only PGAS produces these paths — PMMH / PF would need
  the latent-trajectory consolidation
  (`2026-06-09-latent-trajectory-output-consolidation.md`).
- **Filtering distribution** — _the largest lift._ The bootstrap PF produces
  filtered states but camdl does not currently _save_ them (it keeps the loglik
  and the PGAS-smoothed path, not the filter's per-step marginals). This needs
  new per-step latent output in the filter. Lowest priority of the four.

### Artifact shape

Observation-target objects (free-forward, one-step-ahead) share one
`predictive/<stream>.tsv`, distinguished by the conditioning column — more rows,
not new files. Latent-target objects get a sibling `latent/<state>.tsv` keyed by
`(time, state, <dims…>)` with the same convergence + quantile columns. The
observed series stays in `observed/<stream>.tsv`.

### Naming (open)

The concrete spellings are unsettled and deferred: whether the axis is `horizon`
or `conditioning`; the open-loop label (`free_forward` / `free_run` /
`generative` / `open_loop`); and whether to add an explicit `target` column vs a
separate `latent/` tree. The objects and sources above stand regardless of
label.

## Background: predicted-vs-observed, and the predictive objects

_For a reader new to the workflow; skip if you live in it._

A fit takes a model and the **observed data** — the numbers actually recorded
(say, the count of new Ebola onsets reported in district _Bo_ in week 7) — and
returns a **posterior**: a probability distribution over the model's unknown
parameters given that data.

The first thing anyone does with a posterior is ask: _does the model actually
reproduce the data?_ The universal way to answer is **predicted-vs-observed** —
overlay the observed points on the model's **predictive distribution**, the
range of counts the fitted model says it _would_ produce. Observed points inside
the predicted band mean the model is consistent with the data; points outside
mean it is not. One value over time, observed dots on a predicted ribbon, one
panel per place: this is the workhorse diagnostic, and it is the _same shape_
for every model.

Two terms recur:

- a **stream** is one observed quantity the model is fit to (`onset`, `deaths`);
  a model may have several.
- a stream is indexed by **dimensions** — here `patch` (district) — and each
  combination of levels is a **stratum** (district _Bo_). "Per-district onset"
  is the `onset` stream with `index_dims = [patch]`; a single national series is
  the same stream with no index dims.

### A "predictive" varies on two independent axes

The mistake to avoid up front: "predictive" is not one object. A predictive
varies on **two independent axes**, and the dangerous bugs come from leaving the
second one implicit.

- **Horizon — _what_ is predicted.** _Free-forward_: run the fitted model
  forward from the start and see what data it generates (the generative check).
  _One-step-ahead_: given everything observed up to last week, predict this week
  (the honest short-horizon forecast). _Latent_: not an observable at all, but
  the hidden true incidence behind the reported, under-counted cases.
- **Parameter treatment — _how_ we handle our uncertainty about the
  parameters.** _Posterior_: average over the whole posterior cloud of parameter
  values, so the band carries our full uncertainty. _Plug-in_: run at a single
  best-guess parameter, which makes the band **narrower** because it pretends we
  know the parameters exactly.

These two axes are orthogonal, and the second is the one that bites. camdl's
existing one-step-ahead output (gh#269) is _plug-in_; a free-forward posterior
predictive is _posterior_. If both land in one table looking identical, a reader
compares an honestly-wide band against an artificially-narrow one and reads the
gap as science. Worse, running free-forward at a single plug-in parameter is
exactly the "median smear" mistake that has already produced a wrong figure (see
the correctness section). So this proposal makes the parameter treatment an
explicit, typed part of every predictive object — never an implicit consequence
of which code path produced it.

## The shape of the problem

A camdl fit produces a posterior. Almost everything an analyst does _next_ —
predicted-vs-observed panels, posterior latent incidence, calibration checks —
is a predictive object per `(time, stratum)`. camdl owns every input to that
object (the draws, the fixed parameters, the observation model, the dimensions,
the observation cadence) but hands back none of it assembled. So the analyst
reconstructs it by hand, and the same reconstruction is rebuilt in every
analysis script.

This proposal is grounded in field evidence from an external consumer codebase:
a 14-district spatial SEIRD built on camdl, whose predictive post-processing
grew to **twelve scripts that each shell `camdl simulate` to rebuild
predictions**, plus a hand-rolled module whose only job is to paper over the
gaps. (The evidence lives in that codebase's friction log, not this repo, so the
specific findings below are reported, not repo-verifiable; the design
conclusions stand on their own.) An audit of that code found reconstructions
that pass review and yet are wrong.

### The reconstruction, as one pipeline

Every predicted-vs-observed panel runs the same steps. Annotated with _what
camdl already knows but does not hand over_:

| Hand-written step (every script)                                                                  | What camdl already has               |
| ------------------------------------------------------------------------------------------------- | ------------------------------------ |
| glob the run store for the per-chain `trace.tsv`, guard torn lines, skip the empty resume-stub    | the run-store layout                 |
| filter out burn-in, concatenate chains, subsample                                                 | the declared `burn_in`               |
| **re-inject the fixed parameters** as constant columns, because the trace carries only estimated  | the `[fixed]` block (#273)           |
| write a draws file, shell `simulate --draws … --obs-only-dir`                                     | the predictive engine (exists)       |
| per stream: read the file, prefix-match the value column, pivot wide, float-sort the time headers | the stream list + dims (#279 schema) |
| quantile across draws → ribbon                                                                    | a quantile reduction (trivial)       |

The hand-rolled module's own docstring admits it exists "as a bridge while
camdl#86 is open." gh#86 has since landed, so that piece is now dead code that
re-declares the model's priors in a second place. The consumer has already
designed for camdl to absorb this work.

## Why this is a correctness problem, not just ergonomics

The audit found three reconstructions that pass review and yet are wrong. Each
has the same shape: **camdl knows X, the analyst re-encoded X by hand, and the
re-encoding was wrong.** The three split cleanly into "fixed by the types in
this proposal" and "motivates the deferred guardrail."

1. **Bands from non-stationary draws** — quantiles taken over a hand-picked,
   pre-burn-in window (with one "stuck" chain dropped by eye). Warm-up draws are
   not samples from the posterior, so the band is not a posterior band at all.
   _(Convergence — motivates the deferred guardrail below.)_
2. **Burn-in as a per-script literal** — a hardcoded discard count that drifts
   from the fit's own `burn_in`. _(Convergence — deferred guardrail.)_
3. **A "latent state" figure built at the posterior _median_ parameter** — one
   plug-in parameter vector, presented as the posterior latent state. It
   discards all parameter uncertainty, and the median-of-marginals is not even a
   posterior point. _(Parameter treatment — **fixed in the core by the types
   below**: a plug-in band can never be produced silently or mislabeled as
   posterior.)_

## Design — types first

The CLI is a projection of these types. Define the types, and the clean dispatch
and the impossible-states fall out.

### The core types

```rust
// What a fit actually produced. Resolved ONCE, at the boundary — by ARTIFACT
// (does the chosen stage have a draws cloud?), not by method name.
enum FitResult {
    Posterior(PosteriorDraws),   // PGAS, PMMH, Mh — a draws.tsv exists
    PointEstimate(Theta),        // IF2, NLopt — one best answer, no cloud
}
// A stage with neither — a stand-alone PFilter, which scores at a fixed point and
// writes no draws — is not a FitResult; predict errors, same as the MLE case.

// How a predictive treats parameter uncertainty. The safety-critical axis.
enum ParamTreatment {
    Posterior(PosteriorDraws),   // average over the cloud — full uncertainty
    PlugIn(Theta),               // one parameter — narrower; now it is NAMED, not implicit
}

enum Horizon { FreeForward, OneStepAhead /* , KStepAhead, … */ }

// The output object. You cannot build one without stating its horizon, how it
// treated parameters, AND its convergence — none optional, so none can be guessed
// downstream.
struct Predictive {
    horizon: Horizon,
    treatment: ParamTreatment,
    convergence: ConvergenceStatus,   // every band carries its own R̂/ESS
    // … the per-(time, stratum) quantiles
}

// The NUMBER travels with the band in v1; there is NO refusal policy in v1 — that
// judgment (what threshold, refuse or warn) is the deferred guardrail below.
enum ConvergenceStatus {
    Reported { rhat_max: f64, ess_min: f64 },  // copied from the stage's own summary
    NotAssessed,                               // no per-stage R̂ available
}
```

### Why this makes the bad states unrepresentable

The verb body is one total match, and three properties fall out:

```rust
fn predict(fit: FitResult, horizon: Horizon) -> Predictive {
    let treatment = match fit {
        FitResult::Posterior(draws)     => ParamTreatment::Posterior(draws),
        FitResult::PointEstimate(theta) => ParamTreatment::PlugIn(theta),
    };
    // …
}
```

1. **"Posterior predictive from a point-estimate fit" does not compile.**
   `ParamTreatment::Posterior` _requires_ `PosteriorDraws`. An IF2/NLopt fit is
   a `PointEstimate` with no draws, so it can only ever yield a `PlugIn` band —
   by the type, not a runtime check, and never a silent fallback to a single
   parameter dressed up as a posterior (which was bug 3). This is the clean
   method dispatch: the fit's nature decides which treatments exist.
2. **The plug-in band can never be silent or mislabeled.** Asking for a plug-in
   band from a posterior fit (the legitimate "just run it at the mean, I know
   what I'm doing" case) is _representable_ but requires writing `PlugIn`
   explicitly, and the output carries that label. Honest, never accidental.
3. **`FitResult` already exists implicitly, and is resolved by artifact.** A
   Bayesian stage (PGAS/PMMH/Mh) writes a draws file; an optimizer stage
   (IF2/NLopt) writes a single-point file; a stand-alone PFilter writes neither.
   Because a fit is multi-stage, `predict` resolves **the terminal stage that
   produced draws** (overridable with `--stage`), and errors loudly when there
   is none or the choice is ambiguous — never silently picking one. We name a
   distinction camdl already makes in which artifact it wrote, and parse it once
   at the boundary so downstream never re-checks it.

### v1 scope (minimal)

v1 ships exactly one cell: **`FreeForward` × `Posterior`** — the free-forward
posterior predictive that collapses the twelve scripts. The other cells are real
and the types accommodate them, but they land later:

- `OneStepAhead × PlugIn` already exists separately (gh#269); folding it into
  the same artifact is a later step.
- `PointEstimate` fits (IF2/NLopt) and a stand-alone `PFilter` stage (no draws)
  get a **clear, actionable error** in v1 — _"IF2 is an optimizer: it returns a
  single best-fit parameter set, not a distribution, so there is no band to
  draw. Get those parameters with `camdl fit summary <run> --params-only` and
  run `camdl simulate model.camdl --params … --obs-only-dir out/`."_ Not a
  silent plug-in. Labeled plug-in support for them is a future cell the types
  already allow.
- `Latent` is deferred (it depends on trajectory coherence, #270/#267).

### 1. The run's observation/dimension schema

Per fit, emit a machine-readable descriptor of structure camdl already holds:
per stream, its index dimensions, the dimension levels, the value kind, and the
likelihood. A consumer can then facet a stream by its `index_dims` and label
panels by level names _for any model, with no DSL parsing_.

```json
{
  "schema": {
    "dimensions": { "patch": { "levels": ["Bo", "Bombali", "..."] } },
    "streams": [
      {
        "name": "onset",
        "index_dims": ["patch"],
        "value_column": "onset",
        "value_kind": "count",
        "likelihood": "neg_binomial"
      }
    ],
    "parameters": {
      "estimated": ["R0", "kappa", "rho", "..."],
      "fixed": { "sigma": 0.11, "gamma": 0.13, "ifr": 0.67 }
    }
  }
}
```

It lives in the run's `fit.meta.json` — consumers already read that file (it
already carries the `estimated`/`fixed` parameter roles, so the pairplot
role-marking is half-built; `streams`/`dimensions` are the new fields).

**The logical structure is retained, so this is a mechanical projection — not a
fragile reconstruction.** Expansion turns `onset[patch]` into per-leaf records,
but each leaf keeps its logical name (`source = "onset"`) and its stratum
(`[{dim: patch, level: Bo}]`), and the filter's bound stream already holds that
whole IR record. So the descriptor is a pure fold over the bound streams: group
by `source`; `index_dims` = the stratum's dims; `levels` = the union of stratum
levels; `value_kind` and `likelihood` straight off the record. Deriving it from
the **same** bound-observation structure the filter uses means the schema cannot
disagree with what was fit — pinned by a cheap equality test. (This is the
safest of the new pieces, not the riskiest.)

### 2. `camdl fit predict` — the verb

One verb owns the reconstruction:

- **Resolves the posterior from the run.** Reads the canonical post-warm-up
  draws the terminal Bayesian stage already wrote (burn-in already applied — it
  does _not_ re-apply `burn_in` and double-discard), across chains, from the
  stable store path. On a multi-stage fit it takes the last stage that produced
  draws, overridable with `--stage`, and errors on ambiguity rather than
  guessing.
- **Fills missing parameters from the fit (#273).** Backfills any parameter
  _absent_ from the draws source from `[fixed]`, never overwriting a present
  column. Precedence follows the existing `simulate --draws` engine (so the two
  verbs don't diverge): `--scenario` > a column present in the draws > `[fixed]`
  backfill — i.e. a posterior draw wins over a bare `--param`, which is what you
  want for a posterior predictive. A parameter that is both estimated (present
  in the draws) _and_ in `[fixed]` is a hard error — a genuine contradiction —
  distinct from the existing fit.toml `[fixed]`∩`[estimate]` overlap, which only
  warns.
- **Samples `y_rep`, never the projected mean.** Each draw produces a _sampled_
  replicate through the real observation model (process + observation noise),
  not the expected value. This is load-bearing for ODE backends, where the
  trajectory is deterministic given the parameters, so the projected mean would
  collapse the band and drop all observation variance.
- **Integrates over the posterior** by pooling those sampled replicates across
  draws, then quantiling — the Monte-Carlo posterior predictive, never a single
  plug-in point.
- **Aligned to the observation cadence**, since camdl knows it.

### 3. The artifact

Per stream, a tidy long table, written through the project's existing long
trajectory/obs writer (see the writer-unification dependency below), at a **flat
per-run path** so a consumer never re-enters the hash maze:

```
results/fits/<run>-<hash>/predictive/<stream>.tsv      # tidy, plot-ready, DEFAULT
  time | <dims...> | horizon | treatment | rhat_max | q05 | q25 | q50 | q75 | q95
  # horizon=free_forward (generative replay from t0); treatment=posterior (averaged
  #   over the draw cloud). rhat_max = the fit's convergence number, carried not gated.
  # v1 emits free_forward/posterior only; the columns are schema-stable so
  #   one_step / plug_in / latent rows join later.

results/fits/<run>-<hash>/observed/<stream>.tsv        # the observed half of the panel
  time | <dims...> | value

results/fits/<run>-<hash>/predictive_samples/<stream>.parquet   # OPT-IN (--save-samples)
  time | <dims...> | horizon | treatment | draw | value
```

What each file holds:

- **`predictive/<stream>.tsv`** — the model's distribution over the observable,
  summarized as quantiles per `(time, stratum)`: `q50` is the predictive median
  (a marginal quantile of `y_rep`, _not_ a trajectory at any single parameter),
  the `q05…q95` band is what a consumer draws as a ribbon. The `horizon` and
  `treatment` columns (legible values — `free_forward`/`one_step`,
  `posterior`/`plug_in`) make the two axes explicit, so a plug-in band can never
  be read as a posterior band.
- **`observed/<stream>.tsv`** — the observed half of the panel: the recorded
  value per `(time, stratum)`, emitted by the verb in the same tidy keys as
  `predictive` (a _derived_ series from the bound data, not a copy of the source
  file), so a panel renders from the leaf without chasing the original data
  path.
- **`predictive_samples/<stream>.parquet`** — opt-in: the raw per-draw
  replicates behind the quantiles, for anyone computing their own intervals.

To draw the canonical figure a consumer reads two files, joins on
`(time, <dims>)`, and plots `observed` over the `predictive` ribbon, one facet
per stratum — no model knowledge, no likelihood math, no run-store spelunking.

Shape choices: the two axes are **columns, not file-name conventions or separate
files**, so a new predictive cell is more rows / a new enum value, never new
consumer code; quantile levels are **columns** (a small fixed set,
`{05,25,50,75,95}` by default with an opt-in override) because `fill_between`
wants columns; per-draw samples are **opt-in**; and a **stratified stream is one
file with its index dims as key columns** — `deaths[patch, age]` →
`time | patch | age | …` — never a file per stratum.

### 4. `camdl fit latent` — deferred

The posterior latent state from the _conditioned_ trajectories is the third
horizon. It is **deferred and kept off the CLI surface entirely** until
trajectory coherence (#270/#267) lands — a latent extractor over trajectories
with the known directional-conservation violations is worse than none. Specced
here only so the verb family is designed as a whole; not a landed stub.

## Deferred: the convergence guardrail (needs more consideration)

Bugs 1 and 2 above (bands over non-stationary / hand-picked draws) are
convergence problems: a predicted band drawn from a fit that has not settled
down reads as final when it isn't. What's deferred is the **refusal policy** — a
gate that blocks or demands an `--allow-…` flag. What ships in v1 is the
**recorded number** (the `convergence: ConvergenceStatus` field above), because
deferring _that_ would re-open the exact bug. Splitting it this way:

- **v1 carries the number, never gates.** Every `Predictive` carries its own
  R̂/ESS (copied from the stage's existing summary), so the band is never silent
  about whether its fit converged — the original bug was "the figure didn't show
  it," and this shows it. v1 does not refuse, warn-flag, or threshold; it just
  records. (Meanwhile, the thing for a user to check is the fit's own
  convergence report from `camdl fit summary` before trusting the band.)
- **Blocking is probably the wrong instrument anyway.** A downstream `predict`
  that refuses (forcing an `--allow-…` flag for the routine mid-run look) is
  friction for little gain, and such flags get pasted reflexively. Carrying the
  number un-droppably is a stronger property than refusing — it travels
  correctly through every downstream script.
- **It needs a real convergence verdict, which does not yet exist uniformly.** A
  naïve "reuse the fit's R̂ gate" does **not** work: the fit's compound gate
  threshold (`gate.a_thresh`) is an IF2 chain-agreement statistic and is _inert_
  for PGAS/PMMH (their agreement table is empty, so the gate trivially passes).
  The real Bayesian R̂/ESS lives elsewhere (PGAS/PMMH summaries) under a
  different threshold. A correct guardrail must be method-aware and reconcile
  those thresholds — design work in its own right, hence the deferral.

## The workflow, end to end

```console
$ camdl fit run fit.toml --seed 1
… fit complete.  → make a panel with:  camdl fit predict --fit fit.toml --stream onset
```

`fit run` prints the exact follow-up so the user never has to discover the run
hash. Then:

```console
$ camdl fit predict --fit fit.toml --stream onset      # --fit is the friendly form; a run id also works
wrote results/fits/sle-8a3f12b4/predictive/onset.tsv   (horizon=free_forward, treatment=posterior, 14 strata)
wrote results/fits/sle-8a3f12b4/observed/onset.tsv

$ head -3 results/fits/sle-8a3f12b4/predictive/onset.tsv
time  patch    horizon       treatment  rhat_max  q05  q25  q50  q75   q95
7     Bo       free_forward  posterior  1.01      0.0  1.0  3.0  6.0   12.0
7     Bombali  free_forward  posterior  1.01      0.0  0.0  1.0  3.0   7.0
```

A consumer (a plot script, an agent, the watcher) reads **one file** and never
touches the run store, the DSL, or the likelihood:

```python
import polars as pl
pred = pl.read_csv("…/predictive/onset.tsv", separator="\t")   # facet by index_dims (from schema), ribbon from q-cols
obs  = pl.read_csv("…/observed/onset.tsv",   separator="\t")   # overlay; join on (time, patch)
```

Rendering the figure is **out of scope** — the tidy artifact is the deliverable,
and any plotting layer (a script, the watcher, an agent) draws it from these two
files. The loop is closed up to the artifact: `fit run` prints the `fit predict`
command, `fit predict` prints the two paths it wrote.

Re-simulating a raw trace standalone (#273 fill-missing — _future_
`--draws posterior` resolver, step 2):

```console
$ camdl simulate model.camdl --draws tail.tsv --fit fit.toml --obs-only-dir out/
# fills sigma/gamma/ifr/I0 from [fixed]; never overwrites a column present in tail.tsv.
```

Pairplots drop fixed params by role, not by guessing:

```python
import json
roles = json.load(open("…/fit.meta.json"))["schema"]["parameters"]
pairplot(draws, cols=roles["estimated"])           # roles["fixed"] dropped by role
```

## Execution sequence

Ordered by dependency; early items ship in parallel.

1. **#273 — fill missing params from the fit (ship now).**
   `simulate --draws <tsv> --fit <run>` backfills params absent from the draws
   source from `[fixed]`, never overwriting a present column. Self-contained.
2. **Posterior-from-run resolution.** `--draws posterior --fit <run>` resolves
   the canonical post-warm-up draws the stage wrote. (`--draws` today resolves
   only `uniform`/`prior`/file — this is new.)
3. **The schema descriptor (#279 Part 1).** Derive logical streams × dims ×
   levels × value_kind × likelihood from the bound observation structure; pin
   agreement with a test. Gates the stratified-stream ergonomics of step 4.
4. **`camdl fit predict` + the artifact** — `FreeForward × Posterior` only. The
   headline; collapses the twelve scripts. Routes through the existing long
   writer (see dependency). MLE fits error clearly.

## Dependencies and open items

- **Writer unification is a hard prerequisite (not assumed).** Today
  `simulate
  --obs` writes through its own wide writer, the inference path uses
  a different one, and a long trajectory writer is a third. `fit predict` must
  emit through the **one** long writer the model-criticism proposal's open
  question (§A2 of `2026-06-20-model-criticism-outputs.md`) is about unifying —
  not a fourth format. This proposal _depends on_ that decision; it does not
  assume it solved.
- **Run reference (needs a resolution rule).** `--fit fit.toml` is the friendly
  form, but `--fit` already means "a config TOML" on `camdl profile`, and one
  config maps to **many** runs (per seed, per stage) — so `--fit fit.toml` is
  ambiguous the moment you re-run. Rule: if a config resolves to exactly one
  run, use it; if more than one, **error and list them**, requiring a run
  reference (hash prefix or path, matching `camdl show` / `cat`). `fit summary`
  currently takes a directory path, so the `fit` family is not yet uniform and
  should be reconciled to the hash-prefix form.
- **`--stream` accepts either name.** It names the _logical_ stream (`onset`),
  but since the fit side trained users on the expanded names (`onset_Bo`),
  `predict` should accept an expanded name too and map it up to the logical
  stream rather than reject it.
- **Multi-cadence.** With streams on different cadences, `free_forward` rows
  (per stream cadence) and a future `one_step` (union axis) may have different
  time grids in one file; document the raggedness when `one_step` lands.
- **Score columns** (`log_score`/`crps`/`pit`, when added with `one_step`) are
  out-of-sample for `one_step`; for `free_forward` they are _in-sample /
  optimistic_ (not undefined), and for count data must use randomized PIT.
